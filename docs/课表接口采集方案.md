# KeRing 课表接口采集方案

**这份文档只解决一件事：把"从学校教务接口取全校课表"定下来。**
它记录参考项目的采集器是怎么工作的、学校接口的真实行为（含实测证据）、
我们跟参考项目的处理差异，以及落到 KeRing 里的实现方案。

> 与 [开发交接.md](开发交接.md) 的关系：那份讲 KeRing 本身的架构与部署约定，这份讲本次接入的
> 数据源。两份冲突时，以本文档第六节的"待确认"为准——那些是还没定的。

---

## 一、为什么要有这一份

KeRing 现在的数据源是**本地演示文件**：`MainForm.RefreshSchedule` 里写死
`new LocalFileScheduleSource(_config.ScheduleFilePath)`，读的是数据目录下的 `schedule.json`，
首次运行由 `SampleSchedule` 生成 9 个假班级。

这正是 [开发交接.md](开发交接.md) 第八节列的第 1 号待办：**接入正式课表接口**。
接口规则由使用方提供，参考实现是另一个项目——WorkSchedule（私有库）。

本文档的结论全部来自对参考项目源码的阅读和对学校接口的**实测**，不是推测。
实测环境：开发机 `10.40.1.146`（在校园网内），实测日期 2026-09-13。

---

## 二、参考项目是什么

**WorkSchedule**，位于 `C:\Users\user\Desktop\WS\WorkSchedule`（私有仓库，
`github.com/Qiuzizhao/WorkSchedule`）。它是一套完整的课表服务：Python 采集端 + FastAPI 后端 +
React 前端 + React Native App，数据落在 SQLite。

**我们要学的是它的采集端**，代码在 `collector/`：

| 文件 | 作用 |
| --- | --- |
| `collector/src/fetch_schedule.py` | 采集核心，3570 行：登录、抓取、解析、组装、导出、上传 |
| `collector/src/collector_client.py` | 把采集结果上传到后端（HTTP Basic Auth） |
| `collector/agent/` | 常驻 Agent（FastAPI + WebSocket），接受远程"立即采集"命令 |
| `collector/config/` | 账号文件、环境变量、定时计划 |

### 它跑两条链路

**定时采集**是主力：Windows 任务计划程序 → `scripts/auto_update.ps1` → `fetch_schedule.py` →
上传完整快照。当前节奏是**每 15 分钟一次**，`00:00`–`06:00` 静默，另外每天 `08:35`
单独抓一次"学期看板"（抓满整学期 24 周）。

**Agent 常驻**是第二层：本地 FastAPI 服务通过 WebSocket 连后端，让管理后台能远程下发
`collect.start` / `collect.cancel` / `dktk.preflight` 等命令，本机还带一个网页控制台。

### 它一次采六个模块

`timetables`（个人课表，要**逐个教师登录**，账号池在 `config/accounts.json`）、
`open_classes`、`leaves`、`ann_schedule`、`all_schedule`（**全校课表**）、`announcements`。

**KeRing 只需要 `all_schedule` 这一个。** 这条差别很关键：个人课表那条线要拿几十个教师账号
挨个登录、每分钟的采集节奏、以及后端上传和去重，我们全都不需要。

> ⚠ `collector/config/accounts.json` 里明文存着 39 个教师账号（口令是弱口令），已被提交进
> git 历史。仓库是私有的，不算泄露，但**这些文件一个都不要带进 KeRing**——
> 我们根本用不到账号，见第三节。

## 三、接口：新旧两条路，以及现在该走哪条

### 3.1 两条路是什么

| | 老路子 | 新路子（现行） |
| --- | --- | --- |
| 地址 | `dktk/dktkView.asp?keSpan=dktk` | `php/dktk/dktkView.php` |
| 形态 | 服务端渲染的 ASP 页面（HTML） | AJAX 接口，POST 取 JSON |
| 解析方式 | BeautifulSoup 解析 DOM（`extract_all_schedule`） | `json.loads` + 字段映射 |
| 编码 | `gb2312` | `utf-8` |
| 现状 | **数据已冻结，不能用**（见 3.4） | 在用 |

参考项目的迁移发生在 **2026-08-31，commit `7e32a71`**（"adapt all_schedule/specials/leaves to
new PHP dktk AJAX APIs"），提交说明写得很清楚：

> The school migrated the dktk (代课调课) module to PHP + JS: data is now served via AJAX POST JSON
> instead of server-rendered ASP HTML.

同一批迁移里，晨午管理（特殊行）换到 `dktkTools.php`（`keAction=getZdwlEditInit`），
请假换到 `gmexAPI.php`。这三条都是"学校改版，采集端跟进"。

**我们只取 `dktkView.php` 这一条。** 晨午管理和请假都不采，理由见第四节。

### 3.2 新接口怎么调

```
POST http://10.40.1.1/php/dktk/dktkView.php
Content-Type: application/x-www-form-urlencoded
Cookie: usernameEncoded=<用户名的 UTF-8 百分号编码>

keAction=getKeViewInitData&keSpan=dktk&kWeek=<周次>
```

一次请求返回**全校所有班级**，不需要按班循环。

几个必须知道的细节：

- **`keSpan` 只能是 `dktk`。** 传 `all` 会直接 SQL 报错（`Table 'gmexmain.allin...' not found`），
  实测确认。省略 `keSpan` 倒是可以，服务端默认按 `dktk` 处理。
- **`kWeek=0` 是探测用法**，返回体里的 `curKWeek` 就是学校认定的当前周（实测返回 `2`）。
  拿不到 `curKWeek` 时的兜底见 5.3 和 7.4 最后一条。
  `kWeek=20` 这类越界值也能正常返回。
- **Cookie 必须用 UTF-8 百分号编码**，不能用 gb2312——参考项目的代码注释专门强调过这点，
  编码错了服务端认不出用户，会返回非 JSON。

### 3.3 返回值结构

| 字段 | 含义 |
| --- | --- |
| `result` | 1 = 成功，0 = 失败（`msg` 里是原因） |
| `keTableData` | 班级数组，每项 `{className, keVals}` |
| `knPerDay` / `knPerWeek` | 每天节数 / 每周格数（实测 6 / 42） |
| `allTeInfo` | 教师简名 → `{teName, cGroup, ...}`，215 个教师 |
| `dktkInfoAoa` | 调/代/帮/预代课记录，首行是空表头，数据从第 2 行起 |
| `curKWeek` | 学校认定的当前周 |
| `classNum` | 班级数（实测 74） |
| `delWeDay` / `knShowPerDay` / `dbStCol` / `keTableChTitle` | 界面渲染用的杂项，我们不需要 |

**`keVals` 是按天摊平的一维数组，这是最容易看错的地方：**

```
索引 = 天序号 × knPerDay + 节序号        （都从 0 起）
```

以 42 格为例：索引 0–5 是星期一，6–11 是星期二，12–17 星期三，18–23 星期四，
24–29 星期五，30–35 星期六，36–41 星期日。
**它不等于"6 天 × 7 节"，顺序反了就全错。**

**每个格子是压缩过的**，形如 `语菓` = 科目单字 + 教师简名。要还原得查两张表：

- `_DKTK_SUBJECT_MAP`（写死在采集器里）：语→语文、数→数学、英→英语、口→口语、健→健康、
  体→体育、阅→阅读、道→道法、科→科学、探→探索、美→美术、音→音乐、综→综合、劳→劳动、
  电→电脑、书→书法、班→班会
- `allTeInfo`：菓 → 袁艺菓

**我们只查前一张表。** 代码按"**首字 = 科目代号**"拆，取到课程名就把后半截丢掉。
之所以敢这么拆，是因为实测 24 周全部 5.3 万个非空格子**都是两个字符、首字都是已知代号**，
没有例外（见 7.2 第五组测试）。认不出来的首字会把整格原样保留并写进日志，
不会被静默丢掉。

**调代课是叠加上去的**，`keType`：1=代课（红）、2=调课（蓝）、3=帮课（绿）、7=预代课（橙）。
调课会把两个格子的内容**互换**，同周互换标蓝，跨周只影响本周那一侧。

### 3.4 鉴权：不是登录，是一个非空的 cookie（这是本次最关键的发现）

参考项目的代码里写着"新版全校课表始终需要登录"，但后来又发现可以跳过——
**2026-09-08，commit `54c816e`**「轻量全校课表采集也设置 usernameEncoded cookie」，
代码里留下一句日志：`全校课表轻量采集无需登录，直接读取 dktkView`。
那次改动是为了修"调课提交后刷新课表失败"。

**它为什么能跳过，我做了实测**：用三个不同的名字各请求一次第 2 周的全校课表，
把返回的 `keTableData` 取 SHA256 对比：

| cookie 值 | result | 回显 userName | 班级数 | keVals 校验值 |
| --- | --- | --- | --- | --- |
| `test`（假名） | 1 | test | 74 | `398022F357BFC648` |
| `张三`（编的） | 1 | 张三 | 74 | `398022F357BFC648` |
| `邱梓钊`（真实） | 1 | 邱梓钊 | 74 | `398022F357BFC648` |
| 空字符串 | 0 | — | — | 被拒 |
| 一个空格 | 0 | — | — | 被拒 |

**三个名字的课表数据校验值完全一致，只有回显的名字不同。**
说明服务端没有拿这个名字去查身份、也没有按人过滤数据——它只判断"cookie 在不在、非不空"，
然后把名字原样回显到 `userName` / `userBname`，供前端 JS 显示"当前用户"。
之所以能这样，是因为**全校课表本来就不因人而异**，谁都看同一份。

**对 KeRing 的意义（正面）：**

> **我们不需要保存任何教师账号和密码。** 教室里那台机器上不会出现任何教师凭据，
> 这对交付和运维都是很大的优点——少一份泄漏风险，少一个每学期要换的东西。

**但有两条必须记住：**

1. **这是学校当前的实现，不是承诺。** 学校随时可能加真校验。所以实现时失败兜底必须做扎实
   （保留上一份内存数据 + 日志 + 状态栏提示），不能让接口一变 KeRing 就整体失灵。
2. **别用 `test` 这种假名字。** 虽然数据一样，但会在学校服务器日志里留下莫名其妙的用户名。
   建议用我们自己的采集账号名（**只用名字，不带密码**），来源可追溯。

### 3.5 老路子：页面还活着，但数据已经冻结

这一点值得单独写，因为"老路子采集不了"这句话容易理解错——**不是打不开，是不准了**。

实测 `http://10.40.1.1/dktk/dktkView.asp?keSpan=dktk`：

- HTTP 200，395 KB，`text/html`，`<title>keTable</title>`，`charset=gb2312`
- 表格结构完整：`ke1_1` ~ `ke74_42`，74 个班 × 42 格都在
- 带防缓存参数连抓两次，内容**完全一致**

但它是**冻结的老快照**，证据三条：

| 证据 | 老页面 | 新接口 |
| --- | --- | --- |
| 调代课记录 `dktkInfoAoa` | **2 条**（id 5916/5917，很早的记录） | **160 条** |
| 一(1) 班 42 个格子与前者的差异 | 4 格对不上，形态是"两两对调"（调课造成的错位） | — |
| 编码 | `gb2312`，用 gb2312 解码有 114 个字符是坏的（"菓"这类字直接丢），必须用 GBK 才读全 | `utf-8` |

两者记录**一条都对不上**。结论：**老页面不再接收学校的新数据，照它采会采到过期的课表。**

KeRing 走新接口，`extract_all_schedule` 那套 HTML 解析我们不实现。

### 3.6 接口现在的实际数据（2026-09-13 实测）

| 项 | 值 |
| --- | --- |
| 班级数 | **74**（一(1)…一(14)、二(14)、三(14)、四(12)、五(10)、六(10)） |
| 每天节数 `knPerDay` | **6** |
| 每周格数 `knPerWeek` | 42（= 6 × 7 天） |
| 网格形状 | **7 天**（周一…周日） |
| 当前周 `curKWeek` | 2 |
| 周六周日 | **24 周、74 个班里一格都没有** |
| 工作日 | 74 × 5 × 6 = **2220 格，全满**（没有空堂） |

注意最后两行合起来的意思：**接口本身就给了 7 天的位置，是数据里没有周末课**。
所以"保留周末"对我们来说是"解析时不要截断"，而不是"接口现在有周末数据"。

## 四、我们跟参考项目的处理差异

抓取方法照搬（同一套接口、同样的请求参数和 cookie 机制），**数据处理不一样**。

| | 参考项目 | **KeRing** |
| --- | --- | --- |
| 教师信息 | 保留（格子是"课程 教师"，还额外算 `teacher_occupancy` 教师占用表） | **丢弃**，只要课程名 |
| 周末 | 不需要，输出层截断 | **保留**，解析出完整 7 天 |
| 附加时段 | 额外从 `dktkTools.php` 取晨午管理（晨间管理 / 作业 / 课后2） | **不采**，只要那 6 节课 |
| 调代课叠加 | 全量叠加并上色 | **只叠加调课**（keType=2）；代课/帮课/预代课不改课程名，跳过。界面用**蓝字**标出被调过的格子 |
| 数据落地 | 上传后端、算模块 hash 去重、导出 xlsx | 不上传、不导出；课表只放内存 + 一份"上次成功"的缓存（见 7.4） |
| 采集频率 | 每 15 分钟 | 沿用 KeRing 的 `RefreshIntervalMinutes`（默认 30 分钟） |
| 账号 | 39 个教师账号 | **零账号**，一个 usernameEncoded cookie |

### 关于"丢弃教师"，具体怎么丢

格子的原始值是 `语菓`（科目单字 + 教师简名）。参考项目的 `_dktk_slot_to_entry` 会拆成
`"语文 袁艺菓"`，界面和 Excel 都带教师。**我们只做前半步**：查 `_DKTK_SUBJECT_MAP` 得到
课程名，然后**直接返回课程名，不查 `allTeInfo`**。这样连教师表都不用解析。

### 关于"保留周末"

参考项目的采集器里其实**有两套星期常量**：`_DKTK_WEEKDAYS` 是 7 天（全校课表解析用），
但 `WEEKDAY_LABELS = ["周一"…"周五"]` 只有 5 天，Excel 导出、个人课表、前端全用它。
**周末是在输出层被截掉的，不是在抓取层。**

我们保留 7 天，并且：

- 解析时按 `knPerWeek / knPerDay` 推导天数，**不要写死 5 或 7**
- 周末列在界面上仍然按现有约定处理——[开发交接.md](开发交接.md) 第五节第 7 条：
  周六周日都没有课就一起隐藏，任一天有课就一起显示。这条**不改**

于是行为是自洽的：数据里有周末就显示出来打铃，没有就按老样子收起来。

### 关于"节次"——已定：只要那 6 节，不要附加时段

**结论：只要每天 6 节课，不采集晨午管理等附加时段。**

这条跟实测数据正好对上：学校 `knPerDay = 6`，跟 KeRing `GradeSchemes` 里的 6 节**完全一致**，
所以**不需要任何节次过滤**——接口给的 6 节照单全收即可，`GradeSchemes` 也不用改。

所谓"不需要那么多次课"，指的是**附加时段**，也就是参考项目另外从 `dktkTools.php`
（`keAction=getZdwlEditInit`）取的那三行：**晨间管理、作业、课后2**。它们不在
`dktkView.php` 的 6 节网格里，是独立的一条接口，返回结构是"班级 × 星期 → 值班老师"，
跟打铃没有任何关系。

**我们不调那条接口。** 取数只需要 `dktkView.php` 一次 POST 就够。
好处是少一个接口依赖、少一次请求，也少一份要跟着学校改版走的东西。

## 五、落到 KeRing 的方案

### 5.1 只加一个实现类

按 [开发交接.md](开发交接.md) 第五节第 2 条（"数据源以 `IScheduleSource` 为界"），
新增 `App/Schedule/HttpScheduleSource.cs` 实现 `IScheduleSource`，
再让 `MainForm.RefreshSchedule` 通过一个工厂去取数据源，**其余代码不动**。

它负责三件事：

1. **取数**：POST `dktkView.php` 拿当前周的 JSON（**只有这一个接口**，
   不调晨午管理那条 `dktkTools.php`）
2. **解析**：`keTableData` → 每个班一维 7 天 × N 节的网格 → 课程名（**不查教师**）
3. **组装**：填进现有的 `SchoolSchedule` / `SchoolClass` / `CourseEntry` 模型

### 5.2 不需要任何新依赖

`HttpWebRequest` 就够，JSON 用已有的 Newtonsoft.Json。
**单文件约 1 MB 的交付形态不受影响**，也不需要目标机装任何东西。
（对比：参考项目是 Python + requests + BeautifulSoup，我们不复刻技术栈，只复刻抓取路子。）

cookie 直接写 `Cookie` 头，**不要用 `CookieContainer`**——它会对已经百分号编码过的值再处理一次。

### 5.3 几个设计取向

**班级 id 直接用班级名。** 接口只给 `className`（"一(1)"），没有稳定 id。
现有模型的 `SchoolClass.Id` 用来记住"这台机器是哪个班"，名字当 id 的代价是：
学校改班级命名会导致所有机器要重选。这一点后面可以再议（见待确认）。

**时刻仍然由 `GradeSchemes` 决定，用哪套由班级推出来。** 接口只回答"第几节上什么课"，没有时刻，
这跟 [开发交接.md](开发交接.md) 第五节第 1 条本来就一致。
两套时间表已经换成学校给的《作息时间表（2026 年秋季学期）》（只取第 1~6 节正课），
并且**一二年级自动用低年级表、三到六年级自动用高年级表**（`GradeSchemes.SchemeForClass`，
按班级名首字判断）。设置对话框里那个手选项已经改成只读显示。

> 补充一个实测结论：两套时间表的**上课开始时刻完全一样**（08:50 / 09:40 / 10:35 / 11:25 / 14:20 / 15:05），
> 差别只在每节**时长**——低年级 35 分钟、高年级前四节 40 分钟。所以打铃时刻其实是相同的，
> 班级联动影响的是"正在上的课"标红区间和界面上显示的结束时刻。

**周次以接口的 `curKWeek` 为准**（`kWeek=0` 探测一次）。参考项目早期曾遇到 `curKWeek` 恒为 0
的情况（commit `a27ed77` 因此默认退回第 1 周），但我实测现在是正常的（返回 2/3）。
拿不到时的兜底改成了"**按缓存里的周次往后推**"，见 7.4 最后一条——不再直接退回第 1 周，
那等于拿开学第一周的课表去排铃。

**失败兜底沿用现有行为**：保留上一份内存数据继续跑，走日志 + 状态栏，不弹窗打断无人值守运行。

**调代课只叠加"调课"，其余三种跳过。** `dktkInfoAoa` 里 `keType` 有四种：1 代课、2 调课、
3 帮课、7 预代课。代课/帮课/预代课都只是**换人**，课还是那节课、课程名不变——参考项目会把整格
改写成"代某某"（它要显示代课老师），对我们没意义，直接跳过。**调课不一样：它把两个格子的内容
互换**，课真的挪到了别的节次，会改变"这一节有没有课、该不该打铃"，所以必须叠加。
我们只搬课程名，不搬参考项目那套背景/边框标记。

**调课的格子界面上用蓝色字体标出来。** 跟另外两种标记并列：红底=正在上的课、
绿底=下一个提醒点、**蓝字=这一格被调课动过**。参考项目用的是 `#0000FF`，
我们取 `Color.FromArgb(21, 101, 192)`（正蓝，白底上看得清，也不至于扎眼）。
高亮（红底/绿底）优先于蓝字——高亮撤掉时会再把蓝字恢复回来。

### 7.3 一个顺带必须做的改动

这条已经写进 [开发交接.md](开发交接.md) 第五节第 12 条。

### 7.4 取数链路的五个加固（第二轮）

链路跑通后回头复审，补了五处——都是"教室里真会碰上的事"：

| # | 问题 | 做法 | 验证 |
| --- | --- | --- | --- |
| 1 | **失败后要等满整个刷新间隔才重试**。开机撞上交换机还没起来 → 取数失败 → 下一次已是 30 分钟后，**第一节课的铃就漏了** | 失败后短退避：1 → 2 → 5 → 10 分钟，再不成才回到正常间隔 | 实测失败于 `00:10:07`，重试在 `00:11:07`（+60 秒）、`00:13:07`（+120 秒）✓ |
| 2 | **没有本地缓存**。开机取不到就一个铃都不响（原来数据源是本地文件，现在换成网络，"读不到"的含义完全变了） | 每次成功落一份 `schedule-cache.json`；开机先拿它顶上，接口通了自动替换 | 把接口指向不可达地址后启动：界面立刻用缓存填满，状态栏 `数据：缓存 09-14 00:09`，日志 `已载入课表缓存` ✓ |
| 3 | **跨周不敏感**。调课是按周的，周日夜跨到周一后要等下一次刷新才换新课表 | 日期一变就强制刷一次（成本极低） | 代码路径确认（改系统日期不便实测） |
| 4 | **更新中没有任何反馈**，点"更新课表"像没反应，最坏要等 40 秒 | 状态栏四态：`更新中…` / `正常 xx:xx` / `缓存 xx:xx` / `失败（上次 xx:xx）`，完整原因放悬停提示 | 三种状态都在截图里出现过 ✓ |
| 5 | **空课表会把有效数据换掉**（接口抽风时静默变成空白，铃全不响） | 两层防护：整所学校一条课都没有 → 取数层判失败；选中的班周一到周五全空 → 界面层**不覆盖**现有数据 | 假接口让"测试班"全空：日志 `接口返回的课表里这个班周一到周五一节都没有，已忽略（保留现有课表）`，界面仍是缓存内容 ✓。再让整所学校全空：`接口返回的课表是空的（整所学校一条课都没有），已忽略这一次` ✓ |

第 5 条的两层是有分工的：**取数层**拦"整份数据坏掉"，**界面层**拦"这个班的数据坏掉"。
两个判断都要求"现有课表是有课的"才拦——所以如果这个班本来就合法地没有工作日课程，
不会被误拦（那时新旧都是空的）。

**6. 周次拿不到时的兜底**（第二轮补的第六条）

原来 `curKWeek` 拿不到就**退回第 1 周**——那等于拿开学第一周的课表去排铃，比不给数据还糟
（参考项目就踩过 `curKWeek` 恒为 0 的坑）。现在改成三级：

```
1. 学校接口的 curKWeek          ← 首选，学校说了算
2. 缓存里上次成功的周次 + 相隔周数  ← 兜底（App/Schedule/ScheduleCache.cs 的 TryGetWeek）
3. 第 1 周                        ← 连缓存都没有（从没成功过），日志写明"课表可能是错的"
```

第 2 级为什么按"**周一**"对齐而不是按天数除 7：学校的周次在**周一零点**切换（实测过）。
缓存如果是周五存的，下周一再用，按天数只差 3 天 → 会算成同一周，实际已经差了一周。
按周一对齐就没这个问题。

三种情况都实测过（假接口让 `curKWeek` 恒为 0，看它实际请求了第几周）：

| 缓存 | 期望周次 | 实际请求 | 结果 |
| --- | --- | --- | --- |
| 今天存的第 3 周 | 3 | `kWeek=3` | ✓ |
| 7 天前存的第 3 周 | 4 | `kWeek=4` | ✓ |
| 没有缓存 | 1 | `kWeek=1` | ✓（日志：`也没有可用缓存，只能按第 1 周处理（课表可能是错的）`）|

## 九、时间基准：从服务器校时可靠吗

**起因**：打铃完全依赖"现在几点"，而教室里确实有机器系统时间不准（主板电池没电、时区设错、
从没同步过）。原来的文档里写了一句设想——"最合适的时间源是课表接口的 HTTP `Date` 头"。
那一句**没有验证过**，所以专门测了。

### 结论

**`Date` 头可以当兜底，不能当主源。** 它确实每次都带（成功和失败响应都有），直连时也是实时生成的，
精度 1 秒——问题出在**那台服务器自己的钟慢了 14 秒**：

| 参照 | 本机偏差 |
| --- | --- |
| NTP `ntp.aliyun.com` | **+0.014 秒** |
| 百度 / 腾讯 / 阿里云 的 HTTPS `Date` 头 | −0.4 ~ +0.4 秒 |
| **学校教务服务器 `10.40.1.1`** | **−14.0 秒**（用 1 秒量化做区间交集算出来的，观测期内稳定） |

本机钟是准的，教务服务器慢 14 秒。所以拿它去"校准"会把一个本来准的钟带偏。

### 采用的方案：三个源按优先级取

```
1. NTP 服务器          ← 最可信，误差毫秒级
2. 教务接口 HTTP Date  ← 白捡的（本来就要请求）；但它慢 14 秒，所以只在偏差超过 1 分钟时才采用
3. 本机系统时间        ← 兜底，修正量 0
```

两条重要设计：

- **只算修正量，不改系统时钟。** 改系统时间要管理员权限，而且第 2 个源本身也不完美，
  拿它去改全机的钟会把别的程序一起带偏。
- **时间一律按北京时间（UTC+8）换算**，不跟本机时区走。机器时区设错不该让铃差 8 小时；
  时区不对会在日志和自检里报出来，但不影响打铃。

### 顺带挖出的一个坑：代理

这台开发机开着系统代理（`127.0.0.1:7897`）。走代理请求教务接口时：

- `Date` 头**冻结不动**（8 次请求全是同一个秒值）
- 响应里多一个 `Proxy-Connection: keep-alive`

直连就正常了。程序里原本就设了 `request.Proxy = null`（内网直连，顺便省掉代理探测的等待），
**这次实测正好验证了那个决定是对的**——否则教室里哪台机器配了代理，时间读数就是代理缓存里的旧值。

### 验证（四组）

| 场景 | 做法 | 结果 |
| --- | --- | --- |
| 正常 | 真实接口 + 默认 NTP | `采用：NTP ntp.aliyun.com，修正 +0.02 秒`，总耗时 0.7 秒 |
| NTP 关掉 | `NtpServers` 留空 | 教务接口偏差 14.1 秒 < 1 分钟 → **不采用**，`采用：本机系统时间，修正 0.00`（本机钟没被带偏） |
| NTP 不可达 | 三个不可达地址 | 6.5 秒后放弃（总预算 6 秒），降级到下一级，自检仍返回 0 |
| **本机钟坏了** | 假接口把 `Date` 故意做成慢 10 分钟 | 识别出偏差 600.2 秒 → 采用 → **打铃基准变成本机时间减 10 分钟**，自检里"下一个提醒点还有 8 小时 0 分"同步变成"8 小时 9 分" |

最后一条是关键：它证明修正量真的作用到了打铃逻辑上，而不只是打印出来看看。

| --- | --- | --- |
| `NtpServers` | `ntp.aliyun.com,cn.pool.ntp.org,ntp.ntsc.ac.cn` | 逗号分隔，按顺序试。**教室机器连不上公网 NTP 时，填学校内网的 NTP 或域控地址**；留空则不查 NTP |
| `NtpTimeoutSeconds` | 2 | 每个服务器的等待秒数。NTP 走 UDP，不能用 HTTP 代理，所以超时设得短 |

NTP 有退避：成功过就半小时再查，失败过就两小时再查，不会在不通的网络上每次刷新都白等。
自检报告的 `[10] 时间` 会写明用的是哪个源、偏差多少，部署时看那一栏就知道这台机器的校时状态。
